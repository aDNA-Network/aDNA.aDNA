> the 964-vs-4,444 delta below could not be resolved. Reproducibility is not paperwork.

## The delta is NOT a regression — it is an unreproducible measurement

Every checkable hypothesis for the 3,251 was tested. **All were falsified.**

| Hypothesis | Test | Verdict |
|---|---|---|
| New pages inflated the count | `/learn/tutorials/build-a-lattice` was present in the 08-19 run at **5 errors, zero inline-style**; today **171** | ❌ **falsified** — same page, both runs |
| Shiki version bump via P3.2's lockfile touch (`31b8b53`) | `git show 31b8b53^:site/package-lock.json` vs `31b8b53:` — `shiki` **4.0.2 both sides**, `astro` **6.1.6 both sides** | ❌ **falsified** |
| The page gained code blocks | `build-a-lattice.mdx` — **8 code fences at `31b8b53^`, 8 today** | ❌ **falsified** |
| Highlighting was once disabled and got re-enabled | `git log -S"syntaxHighlight"` and `-S"shiki"` on `astro.config.mjs` — **zero commits ever** | ❌ **falsified** |
| The sweep used a different config | (A) vs (B) above return identical 4,444 | ❌ **falsified for today's tool** |

**What remains, and it is not recoverable from the artifact.** Shiki has been on by default since the
site existed — no `markdown` config block, no `syntaxHighlight` setting, ever. So the 08-19 build
*must* have emitted inline styles too, and the 08-19 *measurement* must have excluded them: a CLI
flag, a config file, or a tool version other than the "11.4.0" typed into the summary table. The raw
artifact records no command line, so the run cannot be re-executed and the question cannot be closed.

⇒ **`no-inline-style` is a standing property of this site, not something that happened to it.**
Recorded as such rather than as a regression, because calling it a regression would be a claim the
evidence does not support — and this campaign's whole aesthetic is that claims move down to
verifiability.

⚠ **The one KW-14 note**: the sweep's "html-validate 11.4.0" may itself be a typed figure. If so it is
the fifth instance this campaign of a number that was written rather than derived.

## ⭐ But the diagnosis found a REAL defect, adjacent and independent

Every code block on this site ships **`github-dark` in BOTH appearances.** `[D]`

```
<pre class="astro-code github-dark" style="background-color:#24292e;color:#e1e4e8;overflow-x:auto">
```

and `grep -rn "astro-code\|shiki" src/styles/*.css src/layouts/*.astro` returns **nothing** — there is
no light-mode handling at all, and an inline style beats a stylesheet rule regardless.

**Be precise about what this is and is not:**

- ❌ **NOT a WCAG contrast failure.** `#e1e4e8` on `#24292e` is a perfectly good ratio — that is what
  `github-dark` is for. This is exactly why **axe passes 0 in both themes**: the block is internally
  consistent. Claiming a contrast violation here would be overclaiming, and the directive's D5 line
  ("*including code blocks, syntax highlighting*") is about the failure SITE, not a guaranteed failure.
- ✅ **IS a dark/light parity break**, and parity is on the campaign's own do-not-regress list. A
  light-mode reader gets a dark slab on 61 pages.
- ✅ **Invisible to every instrument we own.** axe cannot see it (internally consistent), gate-25
  cannot see it (inline attributes, not CSS), `token_aa_check.py` cannot see it (not a token), and
  html-validate flags it only as "an inline style exists" — which says nothing about the theme.

⚠ **And the two issues are INDEPENDENT.** Astro's dual-theme Shiki (`shikiConfig.themes: {light,
dark}`) emits `--shiki-light`/`--shiki-dark` custom properties — **still inline styles**. Fixing
parity does **not** reduce the `no-inline-style` count by one. Anyone reasoning "fix the theme and the
3,251 go away" is wrong, and it is an easy thing to assume.

## Disposition — and the outcome

`no-inline-style` → **documented per-class exception** in `site/.htmlvalidate.cjs`, with its reason
and its reversal condition on the face of the config.

**Final: 4,444 → 0.** All 226 pages clean, `npm run check:markup` exits 0, and the check is in CI.
Fixed at source: `no-implicit-button-type` (227 → 0, **one line** in `Header.astro` plus two static
buttons in `public/install.html`), `unique-landmark` (278 → 0) and `aria-label-misuse` (285 → 7 → 0)
via **one** `SidebarNav` label prop, `no-dup-id` (1 → 0), `long-title` (1 → 0). Exempted with cause:
the three generated classes, the two Safari `role="list"` classes, and `valid-id` **narrowed** to
`relaxed` rather than disabled.

## ⛩ The parity ruling, and what executing it actually cost

Operator ruled **fix now** (2026-08-24). Dual-theme Shiki was configured — **and the first attempt
broke the axe-0 record, which is on the campaign's do-not-regress list.**

`github-light`/`github-dark` are the obvious pair and **both ship token colours below AA at body
size**. Five gate failures. Measured:

| | colour | on | ratio |
|---|---|---|---|
| light | `#e36209` (markdown markers) | `#ffffff` | **3.48:1** |
| dark | `#6A737D` (comments) | `#24292e` | **3.05:1** |

Shipped instead: **`github-light-high-contrast` / `github-dark-high-contrast`**, which exist for
exactly this. Re-measured across **all 58 code-bearing pages, 7 distinct token pairs, both
palettes: 0 failures.** Suite back to **560/560**.

⚠ **The dark failure was ALREADY LIVE and is not something the fix introduced.** The site rendered
`github-dark` in both appearances, so that 3.05:1 comment colour has been shipping — axe never
flagged it because the pages carrying comment-heavy blocks were not in the gate's page list. The
parity fix is what made it visible.

### ⭐⭐ My own measurement was the thing that was wrong, twice

1. **I scanned one page and generalised.** A contrast sweep of `/reference/tool-setup/` returned
   **"light failures: 0"** — true for that page's six token colours, and false for the site. The
   colour that actually failed, `#e36209`, only appears in **markdown-language** blocks, which that
   page does not have. ⇒ **A palette is a property of the corpus, not of a page**; the re-measure
   walks every built page and every distinct pair.
2. **My ad-hoc axe probe reported 71 failing nodes — on nav links, not code.** Pure artifact: it
   drove the theme by toggling a class on a page served by a hand-rolled static server, while the
   real gate is dark-by-default and reaches light by **seeding `localStorage.theme` before load**.
   I nearly chased a phantom nav-contrast defect.
   ⇒ **What settled it was not a better probe but a control**: revert *only* the Shiki change,
   rebuild, re-run the same gate. It passed. That one experiment established causation in a way no
   amount of probing had, and it took less time than the probing did.

⚠ Also worth keeping: `check_aa.luminance` **rejects 3-digit hex** (`#fff` raises `ValueError`).
Shiki emits `background-color:#fff`, so a naive consumer of that function crashes on real input.
Noted for the Vitruvius memo's finding list.
