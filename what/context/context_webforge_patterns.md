# Context — the WebForge pattern relationship

**Plain version**: WebForge.aDNA is the network's web-craft workshop — it maintains proven website templates, a design-token pipeline, a 57-rule quality floor, and performance gates used across the fleet. The adna.network site grew up *beside* that workshop instead of *inside* it, building parallel versions of the same machinery. The HAUSSMANN campaign formally joins the workshop (a federation wrapper + registered consumer row) and adopts its proven parts — and anything the site needs that the workshop lacks gets contributed back, so the whole fleet benefits.

**Technical version**: the full register is `how/campaigns/campaign_haussmann/artifacts/webforge_pattern_register.md` — 15 pattern families with maturity verdicts and adoption gaps. Highlights: the **57-lock craft floor** (13 raise-rounds, census-gated) is already `graduation: offered_to_aDNA.aDNA (Tier 2)`; the **DTCG token pipeline** counts `tokyo_night` (this site's own register) among its ceiling seeds; the **marketplace archetype's reference tenant is literally "aDNA Registry"**; `node_home`'s network map is the proven pattern for the graph page; the provider contract v1.2.0 defines intake (§3), consumer-lane single-build (§4), and vault-manifest pins (§5, ADR-045 placement). The five recurring weakness meta-classes from WebForge's own register (self-certifying gates, lint blind spots, narrated-number drift, literal-pinned live data, bypasses that exit 0) are inherited as standing campaign constraints.

**What we owe back** (`patterns_to_author`): A1 `.md`-twin emission · A2 docs-MCP-server pattern · A3 static registry-JSON emission · A4 proposal-process surface · A5 static network-map variant (if needed) · A6 the TTFS/panel instrument kit — plus live implementation pressure on the proposed-but-unbuilt art-direction ceiling engine (our `art_direction.yaml` entry is its first real test case).
